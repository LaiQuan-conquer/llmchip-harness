# INC-001：Verilator 吞吐事故原因复核与排查修复方案

- 日期：2026-10-31
- 更新：2026-11-01
- 状态：SiLU 条件执行、MAC 门控及 24×4 逐位置回归已有进展；B5/B6 长跑入口、耗时估算和身份校验仍有缺口，P0 未关闭。最新复核见第 16 节。
- 关联目标：INC-001；ADR-012 的 B5 全芯片提示集与 B6 vchip tile 后端验证。
- 原始记录：[INC-001-verilator-tile-throughput.md](INC-001-verilator-tile-throughput.md)。
- 本文范围：记录代码检查、短时性能采样、结论修正及后续实验方法；不修改 RTL、验证判据或验收阈值。

## 1. 结论与下一步

当前结论：**性能修复有效，但尚未完成事故关闭所需的验证**。第 11～12 节记录修复过程与早期缺口，第 13～14 节记录接口、复位、逐位置回归和受控采样的后续进展。第 16 节补充正式长跑入口的阻塞与排期修正；不能把剩余工作简化为“启动后等待 6.8 小时”。

最初建议优先开展**单体模型的 SiLU 条件执行实验**，验证能否消除空闲状态下的大量重复运算。该方向已实施，后续应先补齐验证，再对当前构建重新 profiling。按层分区共仿真保留为备选，暂不作为主修复方案。

依据是：对现有 24 层 MAC 门控实验进程进行 5 秒 CPU 采样后，495 个可执行文件内样本中，有 461 个落在包含 SiLU 运算的生成函数中，约占 93.1%；24 层均有相关采样命中。之前的门控修改只针对 MAC，没有覆盖这一主要热点。

这并不证明 SiLU 独自解释了全部 256 倍差距，也不代表修复后必然恢复单层吞吐。完整运行阶段、缓存开销及修复收益仍需测量。

## 2. 现象与既有实验

下列数据来自原始事故记录，本次分析未重新运行这些基准。

| 构建 | 仿真周期/秒 | 每周期耗时 |
|---|---:|---:|
| 1 层，含 embedding 与 lm_head | 32,918 | 30.4 μs |
| 4 层 | 2,286 | 437 μs |
| 24 层 | 126.1～128.5 | 7.7～7.8 ms |

单层完整 token 为 1,167,833 个 busy 周期、36.4 秒；24 层构建约 58.5 分钟。启动时读取约 1.8 GB hex 的开销，需要与持续运行的每周期成本分开。

既有 MAC 门控实验将乘法移入时序块的 `if (en)`，结果为：单层约 36.1k 周期/秒，24 层约 139.5 周期/秒，后者提升约 10%；该修改已回退。

层数增加 24 倍、每周期耗时增加约 256 倍，说明存在明显的超线性退化。只有这三组数据，不能据此认定算法复杂度严格为平方，也不能确认额外开销全部来自缓存。

本文讨论的是**宿主机执行 RTL 仿真的速度**。它不等于设计的芯片时钟频率，也不直接等于芯片的 token/s。

## 3. 新增代码证据与性能证据

### 3.1 MAC 之外还存在更大的组合计算块

相关源文件：

- [tile_mac.v](../../plugins/rtl-taalas/src/llmchip_rtl/tile/templates/tile_mac.v)：MAC 乘法、组求和及流水线。
- [tile_engine.v](../../plugins/rtl-taalas/src/llmchip_rtl/tile/templates/tile_engine.v)：数据装载、引擎状态及 MAC 使能。
- [tile_silu.v](../../plugins/rtl-taalas/src/llmchip_rtl/tile/templates/tile_silu.v)：整向量组合 SiLU。
- [tile_layer.v](../../plugins/rtl-taalas/src/llmchip_rtl/tile/templates/tile_layer.v)：SiLU 实例与 `S_SILU` 状态的结果采样。

真实 Qwen 构建的 `INTER = 4864`。每个 SiLU lane 包含激活乘 sigmoid、结果再乘 up 分支值两次乘法，以及查表、移位、舍入和饱和处理。

| 每层计算块 | 结构性乘法数量 |
|---|---:|
| 7 个矩阵引擎，每个 128 路 MAC | 896 |
| 4,864 路 SiLU，每路两次乘法 | 9,728 |

这些数量不是等成本的 CPU 指令计数，但说明仅分析 MAC 会遗漏大量工作。24 层 SiLU 合计对应 233,472 个结构性乘法表达式。

层状态机只在 `S_SILU` 中执行 `m_buf <= silu_y`；当前组合 SiLU 的存在时间却不限于这一状态。检查单体生成 C++ 可见，大量 SiLU 运算函数受共同的时钟上升沿／复位触发条件调度，缺少按层或按 SiLU 消费状态跳过计算的保护。

### 3.2 短时 CPU 采样

采样对象是当时已经运行的 24 层 MAC 门控实验进程。该构建的 MAC 乘法已经位于 `if (en)` 内。

| 项目 | 记录 |
|---|---|
| 宿主 PID，仅用于本次溯源 | 59139 |
| 采样方式 | `perf record -e cpu-clock -F 99`，持续 5 秒 |
| 可执行文件内样本 | 495 |
| 采样命中的函数数 | 454 |
| 运行二进制与构建二进制 Build ID | `820703e73eb71b407899d356bae93c341735c3c5`，两者一致 |
| 构建目录 | `/tmp/qwen_build_gated/5b587883ae8cea52/bundle/rtl/obj_tile/` |

通过 ELF 映射基址与 `nm` 符号将采样地址映射到函数，再按相同构建的生成 C++ 函数体分类：

| 函数体类别 | 样本数 | 占比 |
|---|---:|---:|
| SiLU | 461 | 93.1% |
| engine | 8 | 1.6% |
| MAC + engine | 7 | 1.4% |
| SiLU + engine | 2 | 0.4% |
| 其他 | 17 | 3.4% |

SiLU 类别中，有 453 个样本所在函数体仅涉及单层 SiLU，可归属到具体层；另外 8 个样本未纳入单层分布。可归属样本在层 0～23 的数量依次为：

```text
20, 23, 11, 14, 26, 16, 26, 22, 16, 15, 26, 21,
17, 19, 18, 13, 13, 25, 18, 20, 22, 17, 19, 16
```

本次证据的边界：

- 93.1% 是按生成函数体分类的 CPU 时间采样占比，不是逐行测量的 SiLU 乘法占比。
- 未同步记录采样窗口对应的 token、位置及顶层阶段，不能将该占比外推到所有工作负载。
- 采样同时覆盖所有层，结合生成代码，支持“空闲层相关 SiLU 计算仍被执行”的判断；仍应补充受控的空闲与运行分阶段采样。
- WSL 环境未能使用 `instructions`、`cycles` 等硬件事件，未测得指令缓存 miss 或内存带宽占比。
- 曾采样另一个运行进程，但其可执行文件已经被重建替换，不能直接套用其他构建的生成源码分类；本文不使用那组分类结果。

### 3.3 生成代码规模

本次对既有 1／4／24 层构建统计非 `__Slow.cpp` 的 C++ 源文件文本字节数，得到约 32.62／130.71／797.72 MB。

这表明生成代码显著膨胀，但增长量约随层数线性变化，不能据此声称代码量本身平方增长。源文件文本大小也不等于机器码大小或运行时缓存工作集。

## 4. 对原根因解释的修正

| 原有解释 | 复核后的解释 |
|---|---|
| 主要原因已经定位为每层 896 路 MAC 乘法 | MAC 是候选开销之一；门控构建中发现更显著的 SiLU 热点 |
| MAC 门控只有 10% 收益，所以使能门控无效 | 只能证明那次修改收益有限，不能否定其他热点的条件执行 |
| 组合 wire 意味着仿真器必然每周期计算 | 是否求值取决于生成代码的调度和条件保护，需要检查实际 C++ |
| 额外退化已确认来自缓存 | 缓存与代码工作集是合理假设，尚无硬件计数器证据 |
| 分区后约 57 秒/token、20 提示并行约 1 小时 | 尚未实测，不能作为排期或验收承诺 |

目前可支持的原因链条是：大规模复制结构 + 粗粒度触发调度 + 缺少有效条件保护，使大量 SiLU 运算在无须消费结果时仍被执行；代码与数据工作集增大可能进一步放大成本。各因素对 256 倍差距的贡献尚未分解。

## 5. 排查与修复实验

### 实验 A：先建立受控基线

1. 固定模型、权重、数值规格、MAC 数量、上下文长度、编译器及 Verilator 版本；记录 RTL、testbench、二进制和构建参数的哈希。
2. 区分启动装载、复位、空闲 `TICKS`、实际 token 运行四类时间。`TICKS` 是临时调试 testbench 的能力，不能默认生产 bridge 支持它。
3. 对 1／4／24 层分别测量；实际运行至少观察位置 0、32、63，记录 embedding、decoder、final norm、lm_head 等阶段。
4. 同时记录墙钟时间、CPU 时间、RSS、缺页和交换情况；固定 CPU 分配，记录机器上其他仿真任务，避免并发负载污染对照。
5. 采样先从短窗口开始，不必等待一次数小时的完整 token。

示例命令，PID 必须替换为本次启动并核验过的宿主进程：

```bash
perf record -e cpu-clock -F 99 -p <HOST_PID> -o /tmp/inc001-run.perf.data -- sleep 5
perf report -i /tmp/inc001-run.perf.data --stdio --no-children --sort=dso,symbol
readelf -n /proc/<HOST_PID>/exe
readelf -n <BUILD_DIR>/bundle/rtl/obj_tile/Vtile
```

容器路径、已删除的链接器临时文件或重建后的二进制可能导致符号解析失败。此时不能拿其他二进制的源码强行分类；应保留正在运行的 ELF、记录 Build ID，并用对应的 ELF 段映射和符号表解析地址。

### 实验 B：优先实现 SiLU 条件执行

目标：保持完整单体 RTL 仿真，让 SiLU 只在结果确实需要被采样的时刻执行，消除其他状态的大量重复计算。

实施要点：

1. 从 `tile_silu.v` 与 `tile_layer.v` 的 `S_SILU` 消费点入手，设计与原有 `m_buf` 更新绑定的条件计算。
2. 保持现有位宽、符号扩展、溢出、舍入、饱和、LUT 和寄存器采样时刻；避免增加一拍或改变状态机周期数。
3. 只给输入接零、仅门控输出寄存器或加入形式上的 `if`，都不能证明计算已跳过。Verilator 可能仍提前计算中间表达式。
4. 遵守仓库生成硬件规则；不手改生成的 bundle，也不通过在时序块调用带局部变量的 Verilog 函数来规避问题。
5. 检查新生成的 C++，确认查表、乘法、舍入和饱和的主体确实受有效条件保护。若仍位于公共时钟执行路径，实验尚未达到目标。
6. 用同一组负载复测空闲吞吐、运行吞吐和完整 token 耗时，再采样确认热点是否转移。

这是待验证的实现方向，不是已经完成或保证有效的修复。短时 93.1% 的采样占比不能直接换算成实际加速倍数。

### 实验 C：按新热点继续优化

SiLU 实验有效后，再逐项处理新采样中占比最高的部分：

- MAC 乘法、组求和及流水线寄存器。
- engine 中无条件更新的 `word_d`、`x_d` 及相关宽数据搬运。
- KV 读端口的常开使能及相关读取。
- norm、RoPE、残差路径、ROM 读取和其他组合运算。

每次只改一个可独立回退的点。使能必须覆盖有效数据和必要的排空周期；不能直接冻结所有空闲层寄存器。调试或观测输出如果属于判据，也必须保持约定语义。

### 实验 D：编译策略与运行并行度对照

在 RTL 受控的情况下，比较以下配置，不预设收益：

- Verilator 当前 `-O3` 与限制模块内联的配置，例如 `-O3 --inline-mult 2000`；也可对照 `-O2`。
- C++ 的 `-O2`、`-O3`、`-Os`，明确区分 Verilator 优化与 C++ 编译器优化。
- 单体模型 `--threads 1/2/4` 的实际吞吐及资源成本，避免 CPU 超额订阅。

当前 `build_tile` 没有显式指定 `--threads`。`-j` 主要控制构建并行度，不能当作运行时多线程开关；`--output-split` 也不等于跳过空闲层。

构建缓存必须包含完整参数与工具身份；改变选项后需要证明实际运行了新产物。记录构建耗时、机器码大小、RSS 和运行速度，不能只比较编译是否成功。

官方资料说明 `-O3` 当前会启用无限制模块内联，并指出大模型可能受指令缓存限制；这支持开展参数对照，不代表本项目已经验证了相应收益。

## 6. 备选方案及使用条件

| 方案 | 可以尝试解决的问题 | 需要先证明的事项 |
|---|---|---|
| 按层分区共仿真 | 缩小活跃执行代码与工作集，跳过无用评估 | 保留原 RTL 控制语义；验证握手、KV 状态、排空、复位和全局周期一致性 |
| 分层编译 `--hierarchical` | 缓解构建时间与内存压力 | 不等同于按活跃层调度；运行速度未必优于平坦模型 |
| 事件驱动仿真器对照 | 检验对稳定组合逻辑的事件抑制是否更有利 | 用同一 RTL 的小规模和真实尺寸实验测量，不保证更快 |
| FPGA／硬件仿真 | 提高大规模回归吞吐 | 工具、资源和存储适配成本另行评估，不能直接承诺分钟级 |
| 行为模型／数值模型 | 加快软件与数值开发 | 不能未经等价证明就替代 B5/B6 所需 RTL 证据 |

分区并非理论上没有收益，但它不会减少活跃层本身的计算量，还增加编排与等价性验证工作。应在单体热点实验后，依据实际瓶颈再决定是否投入。

## 7. 结果验证与事故关闭条件

以下是验证工作清单，不新增或降低既有硬性验收阈值：

1. 对每个修改先做相关算子与层级验证，覆盖舍入边界、负数、饱和、复位、连续 token、KV 跨位置读写及流水线排空。
2. 比较修改前后以及 GraphL2 的相关数值结果；不能只比较 argmax token。覆盖原判据要求的 logits、中间观测点和周期数。
3. 给出同配置下 1／4／24 层的空闲与实际运行数据、各阶段耗时和热点变化；短时 `TICKS` 提升不等于完整 token 提升。
4. 按仓库规则完成独立评审、相关检查及必要的完整验证。若修改 bridge，执行其要求的完整 conformance；如果规定的代理检查不足以覆盖真实 tile，还要补充 tile 对应验证。
5. 最终仍以 B5 的全芯片提示集及 B6 的对应检查是否完成、数值与周期是否满足既有判据为准。未运行或跳过的检查不能报告为通过。

若 SiLU 条件执行没有改善，应先判断是生成代码仍提前求值，还是热点已经转移；若已经显著改善但仍无法完成回归，再评估多线程、事件驱动对照或分区方案。

## 10. 受控实验：SiLU 置零的单层吞吐（2026-10-31 追加）

按本文实验 B 的前置思路，先把 `tile_silu` 的每路输出置零（仅用于测量，已回退），重建 1 层芯片并测得：

| 1 层构建 | 周期/秒 | 相对 |
|---|---:|---:|
| 真实 SiLU | 36,096 | 1.0× |
| SiLU 置零 | **376,261** | **10.4×** |

结论：SiLU 约占单层每周期成本的 **90%**，与第 3.2 节 93.1% 的采样占比一致；此前只处理 MAC 的 10% 收益因此得到解释。该实验也表明构建时间随之从 121.9 秒降到 35.7 秒（设计规模显著缩小）。

下一步按实验 B 实施条件执行，并以生成 C++ 中 SiLU 主体是否真正位于有效条件内、以及 1/24 层实测吞吐为准，不以“加了 if”作为完成标准。

## 11. 条件 SiLU 的实施尝试与数据（2026-10-31）

按第 5 节实验 B，把 `tile_silu` 改为钟控、带 `en` 的模块（纯函数、无局部变量、计算在 `if (en)` 内），并逐级验证：

| 步骤 | 结果 |
|---|---|
| 8 lane 扫描（a/b 含负数、极值） | 首轮 lane 2/3/4/5/6 失败 |
| 定位 | `silu_z` 用无符号拼接 `{{16{a[15]}}, a}` 与带符号 `LIMIT` 比较，负数被当作巨大正数；改为 `$signed(a)` 比较 |

### 12.2 四项明确缺口

#### 问题一：SiLU 接口变更没有覆盖所有 testbench

证据：当前 `tile_silu` 增加了 `clk/en`，而 [tile_silu_tb.v](../../plugins/rtl-taalas/tests/tile_silu_tb.v) 的 DUT 实例仍只连接 `h1/h3/g`，没有时钟激励，也仍按组合逻辑在 `#1` 后比较结果。

本次实际运行：

```bash
uv run --frozen pytest plugins/rtl-taalas/tests/test_tile_mlp.py -q -x
```

结果：首个 `test_silu_gate_matches_the_model[3]` 失败，64 路结果均为 0，例如 `g[0] = 0, expected 5942`；`1 failed in 7.45s`，退出码 1。由于使用 `-x`，后续用例未运行。本次结果不能表述为“完整单元回归通过”。

修复方法：

1. 搜索所有 `tile_silu` 实例，逐一迁移到钟控接口，不只修改完整层或 attention TB。
2. 在单元 TB 中驱动时钟和使能，在正确时钟沿之后、非阻塞赋值完成后采样；保留原有数值期望，不改为期望 0，也不删除失败用例。
3. 覆盖 `en=0` 保持、连续使能、重新使能、负数、边界值和不同数值参数；复位相关路径在问题三修复后补齐。
4. 重新运行完整 `test_tile_mlp.py` 及受接口变更影响的层、链、芯片测试，区分修复前历史日志与当前构建结果。

这项失败说明接口迁移不完整，不单独证明 SiLU 算术错误；也不能因层级样例通过就忽略它。

#### 问题二：“408 点”来自固定乘数，并非实际检查结果

证据：

- [tile_layer_qwen_tb.v](../../plugins/rtl-taalas/tests/tile_layer_qwen_tb.v) 实际只有 15 组 `CMP`：`h/q/k/v/qr/kr/a/o/x1/h2/g/u/m/f/x2`；`qn/kn` 虽已连接，却没有比较。
- [test_tile_layer_qwen.py](../../plugins/rtl-taalas/tests/test_tile_layer_qwen.py) 写出了 `qn/kn` 的期望文件，但 TB 未读取并比较它们。
- [verify.py](../../plugins/rtl-taalas/src/llmchip_rtl/tile/verify.py) 用固定的 `OBSERVATIONS_PER_LAYER = 17` 乘以通过的层数，生成 `observations` 指标。
- TB 连续驱动位置 0～3，但这 15 组数值比较在循环结束后执行，只检查最后位置的结果；前面位置参与 KV 状态构建，并未逐位置进行同样的数值比较。

因此，当前 24 层通过日志支持的是 **24 个独立层、最后位置、共 360 组向量比较**，不代表完整 24 层串联、所有位置或 408 组实际比较均已覆盖。“组”不是标量元素或单 bit 的计数。

修复方法：

1. 按既有每层 17 观测点的要求补齐 `qn/kn` 检查，包括 Qwen 的旁路语义；不降低验收阈值来匹配当前漏检。
2. 让 TB 显式输出实际执行的检查项、层和位置，由 runner 校验覆盖集合，并据实汇总指标；缺失、重复、跳过或失败的检查不得自动按完整计数报告。
3. 若报告声称逐位置覆盖，需要生成并比较对应位置的 golden，不能只改变报告措辞或乘上位置数量。
4. 重新执行真实权重 24 层回归，保留检查清单和日志；再单独完成全模型端到端测试，不能用逐层测试替代 B5/B6。

#### 问题三：新增 SiLU 寄存器缺少复位

证据：当前 [tile_silu.v](../../plugins/rtl-taalas/src/llmchip_rtl/tile/templates/tile_silu.v) 的 `g_r` 只在 `posedge clk` 且 `en=1` 时赋值，模块没有 reset 输入，也没有输出寄存器的复位分支。

这不符合 [AGENTS.md](../../AGENTS.md) 中普通生成寄存器必须具有复位值的要求；KV 缓存的特定初始化例外不能套用于 SiLU。二态 Verilator 的默认初值不能作为四态上电或中途复位正确性的证明。

修复方法：

1. 为 SiLU 增加与层一致的复位接口和明确的 `g_r` 复位值，并更新全部实例与 TB。
2. 覆盖上电后未使能、首次使能、推理中复位、复位后重跑及输出保持；在相关四态路径验证没有 X 到达观测点。
3. 补齐复位后重新做层级数值、周期和性能对照；不能为了复位或接口迁移额外改变既有层状态机周期数而不验证。

在修改落实前，不能仅凭当前逐层样例宣称该项已符合仓库硬约束。

#### 问题四：计划中的 B5 长测与当前源码没有绑定同一构建

复核时，临时 `/tmp/run_b5.py` 的 `BUILD` 指向 `/tmp/qwen_build/0204ffdd40aed261`。对比发现该目录的 `tile_silu.v` 与当前模板不同：它仍通过带局部变量的 `silu_vec` 函数计算，当前模板已改为时序块内的 lane 循环。

`/tmp/qwen_build_gated/ae932b123d01ecf1` 中的 `tile_silu.v`、`tile_mac.v`、`tile_engine.v`、`tile_layer.v` 与本次检查的当前模板一致；既有真实层测试目录中的这四个文件也一致。这只是部分源码身份核对，不是完整二进制、模型和 golden 绑定证明。

修复方法：

1. 由正式构建流程生成并选择 B5/B6 产物，避免将历史临时目录写死为当前构建。
2. 保存源码／bundle、全部构建输入、工具与参数、二进制 Build ID 或哈希、数值规格和模型权重身份；确认运行进程实际加载了这些产物。

- 根因：测试漏传 `-GPOS`，TB 始终按 4 个位置运行；POS<3 时 `x.hex` 只有 `pos+1` 行，剩余 token 的 `x=0`，最终 `h` 为 0。补上 `-GPOS={pos}` 后，第 0 层 **POS 0/1/2/3 全部通过**（各约 30 秒）。
- **24×4 全量逐位置回归完成：96 passed in 2064.44s (0:34:24)**，即 24 层 × 4 个位置 × 每位置 17 项 = **1632 项实际比较**，全部通过；`LLMCHIP_QWEN_POSES=0,1,2,3` 与 `LLMCHIP_QWEN_LAYERS=0..23` 一次进程内跑完（规格只构建一次）。

## 16. 长跑入口复核、耗时修正与后续方案（2026-11-01）

本节基于本地 `c80be13` 时的代码检查，区分可由代码确认的问题与尚未实测的耗时估算。本次只补充文档，没有修改源码或启动全模型长跑；下列修复方案均为待实施工作。

### 16.1 耗时估算：6.8 小时的适用前提

`64 × 385 / 3600 = 6.84 小时` 只估计了 64 次 RTL step，假设每次耗时恒定为 385 秒。把它解释为 20 提示的总墙钟时间，还要求 20 个实例真正同时执行，并且各实例保持单实例速度。

实际还需计入：

- 输入提示的 prefill；当前 tile 的 prefill 是逐 token 执行 RTL，不是无需耗时的主机装载。
- 上下文位置变化：attention 与 KV 工作量可能随位置增长，385 秒不是所有位置的已测常量。
- 启动读 ROM、复位、L2 golden 生成、比较、回放及结果落盘。
- 多个进程竞争 CPU、缓存与内存带宽的影响；逻辑 CPU 数与内存容量不能直接证明 20 个 worker 都能保持原速度。

按当前 [generator.py](../../python/llmchip-vchip/src/llmchip_vchip/generator.py) 的生成流程，若提示长度为 `L`、实际生成 `G` 个 token、没有提前停止或上下文截断，RTL step 数为 `L - 1 + G`。最后一个提示 token 的 step 产生首个生成 token，不能重复计数。

| 场景 | RTL step 数 | 以恒定 385 秒/step 粗估 |
|---|---:|---:|
| 仅 64 次 step，不计额外 prefill | 64 | 6.84 小时 |
| 50-token 提示，实际生成 64 token | 113 | 12.08 小时/提示 |
| 单次填满 512-token 上下文 | 512 | 54.76 小时 |
| 20 提示、每提示仅计 64 次 step，串行 | 1280 | 136.89 小时，约 5.70 天 |

这些都是算术估算，不是新增实测或承诺。若上下文不是 512，应替换表中的边界测试规模；若提早生成 stop token，应据实记录实际数量，不得直接报告为已完成 64-token 覆盖。

并发数为 `w` 时，应以实际测得的并发吞吐估算总耗时，而非把串行时间直接除以 `w`。原“约 14 GB”仅是容量估计，不代表总峰值、无交换运行或吞吐已得到验证。

### 16.2 阻塞一：正式 bench 的提示处理仍是串行，且包含额外回放

证据：

- [runner.py](../../python/llmchip-vchip/src/llmchip_vchip/runner.py) 的 `Session.generate_all` 对提示列表顺序调用 `generate`，当前没有 20-worker 调度。
- `bench` 除了 DUT 自由生成，还会生成 golden 序列，并让 DUT teacher-force 回放 golden 路径。golden 本身也有相应回放；不能按一次自由生成计算全部开销。
- [conform.py](../../python/llmchip-vchip/src/llmchip_vchip/conform.py) 的 T-04、T-07、T-09 包含重跑／一致性检查；T-05 包含满上下文 prefill，随后还通过 `generate` 再次走满上下文路径。
- 非 quick 的 T-18/T-19 会内部调用 `bench`；若再独立运行同样的 `bench`，会重复执行长测。

修复与排期方法：

1. 按实际调用路径列出每个检查的提示数、prefill 数、decode 数、重复次数及上下文位置，先建立工作量清单。
2. 在正式 runner 中实现按提示分片、每个 worker 独立模拟器与 KV 状态的有界调度；同一提示内部保留 token 串行依赖。
3. 对 1／2／4 等并发配置先测吞吐、RSS、缺页和交换，再根据结果决定是否增加到 8／20。并发实验也需固定输入与产物身份。
4. 让一次正式 `bench` 覆盖符合相同要求的 B5 输出比较证据，并持久化可被关联检查引用的报告。其余复位、确定性和上下文检查仍须独立完成，不能把覆盖不同要求的结果直接复用为通过。
5. 保持现有自由生成与 teacher-forcing 比较的意义，不因运行成本高而删除回放或减少验收覆盖。若要重构重复执行，需证明等价覆盖和结果绑定。

### 16.3 阻塞二：整批 prefill 受单个请求超时限制

证据链：

1. [adapters/process.py](../../python/llmchip-vchip/src/llmchip_vchip/adapters/process.py) 的 `ProcessChip.prefill` 发出一次包含全部 tokens 的请求；`_call` 对整次请求使用一个 deadline。
2. [serve.py](../../python/llmchip-vchip/src/llmchip_vchip/serve.py) 等 `chip.prefill` 全部完成后才发送最终 JSON 响应，没有逐 token 进度返回。
3. [interface.py](../../python/llmchip-vchip/src/llmchip_vchip/interface.py) 的 `BaseChip.prefill` 顺序执行每个 token 的 `step`；TileSim 沿用此实现。
4. [build.py](../../python/llmchip-vchip/src/llmchip_vchip/build.py) 的 `graph_chips` 为 RTL manifest 设置 `timeout_s = 3600`。

按 385 秒/step 粗估，10 个 token 的整批请求已约需 3850 秒；即使每个 step 正常完成，请求也可能在 3600 秒时被判为 timeout 并杀掉进程。更长提示与满上下文测试风险更高。一条真实 `step` 成功，不能证明多 token `prefill` 可以完成。

修复方法：

- 支持有界、可取消的长请求：可以按操作与 token 数计算 deadline，或扩展协议提供可验证的进度／分段响应；设计时保留 prefill 的位置、KV 和逐结果语义。
- 将“任务仍在正常推进”与“单个 step 卡死”分开检测，不能只把全部超时改为无限大。
- 用可控制每步耗时的测试后端验证：长 prefill 正常完成、无进度会超时、子进程退出能被发现、取消能清理容器、顺序和结果数量正确。
- 再做真实模型的多 token prefill 启动检查，然后按既有上下文长度完成边界测试；不通过缩短上下文或跳过 T-05 消除失败。

### 16.4 阻塞三：conform 的 T-17 使用了不匹配的检查集合

证据：当前 `conform.py` 的 `_hardware` 从 [rtl_bridge.py](../../python/llmchip-vchip/src/llmchip_vchip/bridges/rtl_bridge.py) 导入固定的 `HOST_CHECKS`，要求 `status_polled_until_done`、`read_repeatable` 等 SPI／READ 路径检查，并要求返回集合完全相等。

但 [tile_bridge.py](../../python/llmchip-vchip/src/llmchip_vchip/bridges/tile_bridge.py) 的 tile pin-level bridge 目前只声明并返回 `busy_pin_counted`。因此，按当前代码即使长时间生成和比较均成功，T-17 仍会因集合不匹配而失败；后续 `_read_against_golden` 对 READ 路径的适用性也需核对。

修复方法：

1. 先按既有架构、项目接口与验收定义，确认 tile 的并行主机接口需要证明哪些行为；不能仅以当前后端返回了什么来定义通过条件。
2. 在受信任的 harness 端按已验证的接口类型选择检查实现。保留 spatial/SPI 的现有检查，补齐 tile 适用的引脚行为验证。
3. 增加阴性测试：缺少必需项、额外／伪造项、值为 false、仅由芯片自报的通过都应被正确拒绝。不能删除 T-17、直接置 pass，或把缺失项无依据地改为 n/a。
4. 先用小模型完成完整 conformance，避免跑几小时后才暴露静态接口不匹配，再运行真实全模型版本。
5. 若修复涉及检查定义、版本或硬判据，按仓库现有变更规则处理；本文不批准改变验收要求。

**进展（2026-11-01）**：`conform` 的 T-17 改为使用后端声明的检查集合（tile 为 `busy_pin_counted`，spatial 回退到原 SPI 集合），不再固定导入 `rtl_bridge.HOST_CHECKS`；`python/llmchip-vchip/tests` 的 conform/bridge 13 项通过。

### 16.5 阻塞四：身份记录存在，但尚未完成真实性校验

当前 `build_tile` 的实际 tile 命令使用 `--output-split 10000`、`--output-split-cfuncs 1000`；写入 `build.json` 的 `verilator` 字段却引用通用 `FLAGS`，其中是 `20000` 和 `2000`。记录与实际命令不一致。

同时，TileSim 只是读取 `build.json` 并经 hello 上报，没有重新计算二进制／源文件哈希进行比对；身份文件缺失时还会使用空字典。因此，“hello 包含 build 字段”不是当前运行二进制已经得到校验的证明。

修复方法：

1. 从实际执行的命令构造参数记录，包含工具／镜像身份、C++ 参数、top wrapper、testbench、RTL、ROM／权重及其他决定构建结果的输入；构建缓存键也应覆盖实际生效配置。
2. 在启动前校验输入与二进制，拒绝身份缺失或不匹配的正式验收运行；采用只读或受保护的构建产物，必要时核对实际加载进程的 Build ID／哈希。
3. 关联 `run-identity.json`、golden、提示 token IDs、量化／校准规格与实际运行产物，不能只匹配模型名称。
4. 注入替换二进制、篡改参数记录、替换 golden 和缺失身份等情况，验证检查确实拒绝它们。已有记录字段不能仅靠“文件存在”测试判为可信。

**进展（2026-11-01）**：`build.json` 不再记录通用 `FLAGS`，改为记录**实际执行的容器命令**（含 10000/1000 拆分参数、镜像、挂载与源列表），测试断言命令中出现 10000/1000；运行期二进制哈希比对的“篡改/缺失拒绝”测试尚未做。
